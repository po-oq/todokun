  1. memo.md が無い → 何もしない。
  2. memos/*.md にmemo.md と同じバイト列のファイルがある → コピーはせず、memo.md の削除だけを試す（コピー済みで削除に失敗した前回の続き。二重には作らない）。

8中③ 改名中に他の操作が来たときの順番と、確定の二重実行。9 章の「フォーカスが外れたら確定」（docs/memo-list-plan.md:245）は、Enter で確定 → 入力欄が消える → もう一度 LostFocus、と確定が 2 回走りやすい（2 回目は古い名前で Rename して「外で変わった」と失敗を出す）。改名中に別のメモのクリック・✕・Ctrl+N・タブの切り替えが来たときの順番（先に確定するか）も無い。「＋」は「作る → 入力 → 確定したら開く」の 2 段（:174）なので、入力中に別のメモをクリックすると「確定して新しいメモを開く」と「クリックしたメモを開く」がぶつかる。 7.4 に決めごとを足す：
  • CommitRename は冪等：最初に IsRenaming=false にしてから処理し、2 回目は何もしない。改名中の項目は VM に 1 つだけ。
  • Open・Add・Delete・タブ切替の入口で、改名中なら先に同期で確定する。消す対象が改名中の項目なら取消。
  • 「＋」は作った直後にそのメモを開いてから（ビュー・空）入力状態にする。確定・Esc で BeginEdit するだけ。これで「入力中に別のメモをクリック」は普通の切り替え（確認なし。空なので未保存も無い）になる。
  • ダブルクリックの改名は、1 回目のクリックで開けたとき（確認でキャンセルされなかったとき）だけ始める。
9中③ 削除後の「隣」と絞り込みの関係が無い。「隣（一覧で次、無ければ前）を開く。0 件ならメモなし」（docs/memo-list-plan.md:181）は、絞り込み中に最後の 1 件を消したとき、他にメモがあっても「メモなし」になるのか、絞り込みの外のメモを開くのかが決まらない。 「隣はいま見えている並びで選ぶ。見えている並びが 0 件になったら、絞り込みを消さずに『メモなし』（右ペインに『絞り込みに一致するメモがありません』）」など、どちらかに決めて 7.4 に書く。推奨：見えている並びで選ぶ（見えていないメモが急に開くのは分かりにくい）。
10中⑤ 予約名の「拡張子の前の部分」が曖昧で、末尾に _ を付ける方法では直らない場合がある。タイトルはそのまま <タイトル>.md になるので、CON.txt は CON.txt.md。Windows は最初の . の前（CON）で予約名と見なす。計画の「末尾に _」（docs/memo-list-plan.md:133）だと CON.txt_ になり、最初の . の前はまだ CON のまま。COM¹〜COM³・LPT¹〜LPT³（上付き数字）や CONIN$・CONOUT$ も予約されている。 判定は「最初の . の前（後ろの空白を除く）」、直し方は「その部分の直後に _」（CON.txt → CON_.txt、con → con_）。一覧に上付き数字と CONIN$・CONOUT$ を足す。1-1 のテストに CON.txt・nul .md・COM¹ を足す。Windows 実機の確認項目（4-1）にも 1 行。

12中② ⑥ 引き継ぎのお知らせが TODO 側のバーに出て、メモタブでは見えない。起動時のお知らせは 1 つの文字列（AppStartup.cs:14）で、日の編集の Message に入る（MainViewModel.cs:53）。日を開く・編集に入ると消える。データルートが書けないときのお知らせ（AppStartup.cs:51）と引き継ぎの理由をどうまとめるかも無い。 StartupResult に MemoNotice を別に持たせ、Memo.Editor.Message（メモタブのバー）に出す。TODO 側のお知らせはそのまま。「書けない」のときは両方に出る（TODO は今の文、メモは 7.3 の文）。
13中⑤ 大文字小文字だけの改名で一時名を経由すると、途中で止まったときメモが一覧から消える。計画は「一時名経由」（docs/memo-list-plan.md:227）。一時名が .tmp など走査が無視する名前（:143）だと、1 回目の Move と 2 回目の間で止まったとき、ファイルはあるのに一覧に出ず、戻す仕組みも無い。また、mac の APFS はファイル名の Unicode 正規化（NFC と NFD）も区別しないが、大文字小文字を無視した比較だけでは同名と判定できない（入力は NFC、Finder で作ったファイル名は NFD のことがある）。この場合は Move が「既にある」で失敗し、元のまま知らせが出るだけなのでデータは失わない。 まず File.Move(old, new) を直接試す（.NET は Windows・mac で大文字小文字だけの改名を扱える。要確認：1-2 のテストを mac で、Windows 実機で 1 回）。一時名を使うなら、一覧に出る名前（例：<タイトル> (改名中).md）にして、止まっても消えないようにする。同名の判定は OrdinalIgnoreCase の前に NFC にそろえる（Normalize の最初で string.Normalize(NormalizationForm.FormC)）。
14中⑥ 改名の知らせの出し先が計画の中で食い違っていて、計画どおりだと失敗の知らせが消える。7.4 は改名の知らせを「Editor.Message ではなくトースト相当」（docs/memo-list-plan.md:179）、7.6 は「右ペインのバー（Editor.Message）」（:210）。どちらにしても、改名欄からフォーカスが外れて確定 → 失敗 → 続けてクリックしたメモを開くと、ShowContent が Message = null にする（DocumentEditorSession.cs:145）ので、失敗の理由が見えないまま消える。開いていないメモの削除に失敗したときも、出る場所が開いているメモのバー（:183）で、どのメモの話か分からない。 一覧で起きたこと（改名の置き換え・同名・改名と削除の失敗）は一覧の上に出す知らせ（MemoListViewModel.Notice。次の一覧の操作か数秒で消える）にし、Editor.Message は開いているメモの読み書き（保存・読めない・チェック）に使う、と分ける。文には必ずメモの名前を入れる（「『会議』を削除できませんでした：…」）。7.4・7.6 を同じ記述にそろえ、図解 HTML も直す。

17低④ Delete・F2 の対象が「開いているメモ」で、キーボードで選んだ項目ではない。計画は ↑↓ が効かなければ「Tab ＋ Enter で操作できることを正とする」（docs/memo-list-plan.md:204）。Tab で項目 B にフォーカスを移して Delete を押すと、開いている A が消える（確認ダイアログに名前が出るので、気づけば止められる）。mac のキーボードには Delete キーが無い（fn＋⌫）。 フォーカスが一覧の項目にあるときは、その項目（DataContext の MemoListItem）を対象にする。それ以外は開いているメモ。mac は Cmd+⌫ も Delete と同じに扱う（Finder と同じ）。
18低④ 改名欄と検索欄のキーの受け方が書かれていない。ウィンドウの Tunnel は ImeProcessed を捨てる（MainWindow.axaml.cs:67）が、改名欄・検索欄の Enter／Esc は自分の KeyDown で受ける。編集欄の Esc は「Bubble で、まだ処理されていないときだけ」にして、IME の取消の Esc を通している（Views/DocumentPaneView.axaml.cs:70-78）。改名欄で Tunnel を使うと、IME の変換確定の Enter で名前が確定するおそれがある（mac は ImeProcessed にならない場合あり。要確認）。 7.5 に「改名欄・検索欄の Enter／Esc は、編集欄の Esc と同じく Bubble・!e.Handled・ImeProcessed を除く」と書く。変換中にフォーカスが外れたときは、確定前の文字を含めない（Avalonia が確定してから LostFocus を出すかは要確認。Windows 実機の項目に足す）。
19低⑥ 抜粋の「緩く読む」と「（読めません）」が両立しない。4 KB で切ると UTF-8 の途中で切れる。7.2 は「不正なバイトは ? で置き換える」と「UTF-8 として読めない本文は『（読めません）』」を両方書いている（docs/memo-list-plan.md:144）。緩く読むと、読めないかどうかが分からない。4 KB ちょうどで切ると、正しいファイルでも最後の文字が途中で切れて、厳しく読むと「読めない」になる。 厳しい Decoder に flush: false で 4 KB を渡す（最後の途中の文字は持ち越されて誤判定しない）。例外なら「（読めません）」、BOM は飛ばす。「緩く」の 1 文は消す。
20低① 改名した後の見出しとプレビューの更新が書かれていない。HeaderText は基底では通知されない（DocumentEditorSession.cs:76。日は OnDayChanged で通知している DayEditorSession.cs:28-32）。画面は Editor.HeaderText に結び付いている（Views/DocumentPaneView.axaml:11）。ビューのときは、プレビューのページの場所（CacheKey）も古いまま。 2-2 の RenameTo に「HeaderText と Title を通知する。ビューのときは ContentChanged(true) で作り直す（編集中は何もしない）」と書く。_generation は増やさない（確認ダイアログ中に改名されても、保存は新しい名前に書けばよい）—この点は計画どおりで正しい。

5. 計画で決めたこと（9 章）について

決めごと判定所見と提案
起動時は一覧の先頭（最後に保存したメモ）を開く（docs/memo-list-plan.md:244）要件と違う要件（memo-list-requirements.md:91）とデザイン案は「最後に開いていたメモ」。「更新順なら先頭がほぼ同じ」という理由は弱い：読むだけ（ビュー）では更新日時が変わらないので、毎日「コマンド集」を見る人は、最後に書いた「買い物」で毎回起動することになる。逆に、チェックボックスを 1 つ押しただけで先頭が変わる。保存先は新しく要るが、cache/（マシンごと・消してよい場所。todo-requirements.md:39）に名前 1 行を書くだけで足り、読めなければ先頭に戻せばよいので小さい。下の Q1。
名前変更でフォーカスが外れたら確定（:245）妥当要件は「Enter 確定・Esc 取消」だけで、外れたときは決めていない。打った文字を失わない方を取るのは、要件の「止められたくない」に合う。ただし #8（二重の確定・他の操作との順番）と #18（変換中の文字）を決めること。デザイン案の HTML を 4-1 で揃えるのも計画どおりでよい。

未保存で「＋」を押したら確認（:251）妥当別のメモへ移るときと同じ確認なので、覚えることが増えない。デザイン案（トーストだけ）より安全。#8 の「作ったらすぐ開く」形にすると、「確認 → 作る → 開く」が 1 本の流れになる。

6. 決めたいこと

Q1. 起動時に開くメモ
A) 最後に開いていたメモを cache/ に 1 行で覚える（読めない・無ければ先頭）… 利点：要件どおり。見るだけのメモでも戻れる／欠点：小さな保存先が 1 つ増える（2-4 に 1 コミット分）
B) 計画どおり先頭（最後に保存したメモ）… 利点：保存先が増えない／欠点：要件と違う。要件を 4-1 で書き換える必要がある
推奨：A（手間が小さく、要件とデザイン案の両方に合う。データルートではなく cache/ なので同期フォルダを汚さない）
Q2. WebView にフォーカスがあるときの Ctrl/Cmd+N・F（#3）
A) 両 OS で効かせる（mac は届いたキーを使う、Windows はページから転送。重複は短い間で捨てる）… 利点：要件どおり、ビューを読みながら追加・検索できる／欠点：KeyForwarderScript・PageKey を触る。Windows 実機の確認が要る
B) 効かせない（計画どおり）… 利点：変更が少ない／欠点：本文をクリックした後は毎回、一覧をクリックし直す必要がある。要件に例外を書く
推奨：A
Q3. データルートが書けないときの古いメモ（7.3）
A) 計画どおり、知らせるだけで表示しない
B) memo.md を読み取り専用の 1 項目として一覧に出す（引き継ぎはしない）… TODO が「閲覧はできます」（AppStartup.cs:51）なのとそろう／一覧に特別な項目が 1 つ増える
推奨：A（まれな場面で、データは失わない。B は使われてから考えればよい）
